Why

목적과 못 박은 원칙 5가지

EKS 운영 역량 확보가 1순위. ECS 마이그레이션은 검증 수단이다. 그래서 관리형 서비스와 EKS Auto Mode를 의도적으로 배제했다 — 운영 부담이 비용이 아니라 목적이다.

1

클러스터는 소모품이다

이름에 시퀀스 번호(-01). 클러스터 안에 상태 없음, 모든 것이 Git에, DNS는 클러스터에 안 묶임. 예외: 허브는 소모품이 아니다 (ArgoCD·Thanos·Vault 상태 보유).

2

Terraform / GitOps 경계 = 수명주기

계정·클러스터보다 오래 사는 것은 Terraform, 워크로드 수명주기를 따르는 것은 GitOps. helm_release·kubernetes_manifest 금지, 예외 0개.

3

환경은 디렉토리다, 브랜치가 아니다

main 하나. dev/qa/uat/prod 는 namespace + overlay 디렉토리.

4

이미지 태그는 불변

ECR IMMUTABLE, sha-<gitsha>. 승격은 태그가 아니라 digest(@sha256:). latest 금지.

5

관측이 워크로드보다 먼저

로그·메트릭이 돌기 전에 어떤 서비스도 올리지 않는다 — 그래서 관측 스택이 Phase B(허브)에 있다.

Observability · Scaling

Thanos 확장 — 무상태는 자동(HPA), 상태는 수동

쓰기: Prometheus → Receive Router(hashring 라우팅) → Ingestor(TSDB 저장·S3 업로드). 읽기: Grafana → Query가 fan-out → 최근은 Ingestor, 과거는 Store Gateway(S3) → 병합.

📖 읽기·라우팅 — 무상태 → HPA 자동

  • Query — 여러 소스에 동시 질의·병합. Grafana 창구 → HPA
  • Query Frontend — 쿼리 캐싱·시간분할·재시도 → HPA
  • Receive Router — remote_write 받아 hashring으로 라우팅만 → HPA
  • 무상태(데이터 안 들고 있음) → 파드 막 늘려도 안전

✍️🗄️ 저장 — 상태 → 수동

  • Receive Ingestor — 실시간 TSDB 저장 + S3 업로드. replicas=샤드 수, replicationFactor=복제. 수동 resharding
  • Store Gateway — S3 과거 블록 조회 제공. 수동 샤딩
  • Compactor — S3 압축·다운샘플·retention. 버킷당 1개 ⛔ (2개면 블록 손상)
  • 상태(데이터 보유) → 파드 수 변하면 재분배 → HPA 금지, 미리 넉넉히
원리 — 무상태는 그때그때 fan-out만 하니 HPA로 자동 확장, 상태(Ingestor·Store)는 데이터를 들고 있어 파드 수가 바뀌면 hashring 재분배가 필요 → 계획적 수동 확장. Compactor는 동시성 자체가 위험해 항상 1개. 우리 설정: 무상태 3종 HPA + Ingestor 3샤드 · RF 2(분산+HA).
Observability · Cross-cluster

스포크 → 허브 관측 연결 — Receive vs Sidecar

크로스클러스터라 어느 쪽이든 NLB(내부)가 필요. 차이는 "누가 S3에 올리고, 실시간을 어디서 서빙하냐" — 부하 분산 때문에 Sidecar+NLB 채택.

Receive + NLB — 중앙집중

스포크 Prometheus ─(NLB)→ 허브 Receive Router
→ 허브 Ingestor (TSDB 저장) → S3 업로드
  • 받기·S3 업로드 모두 허브. 스포크는 push만
  • 모든 클러스터 시계열이 허브 Receive로 몰림 → 중앙 부하

Sidecar + NLB — 분산 ✅ 채택

스포크 Prometheus + sidecar ┬→ S3 직접 업로드
└→ Store API :10901 ←(NLB)← 허브 Query 실시간 조회
  • 스포크가 자기 데이터 자기가 S3에 올림 → 중앙 부하 없음
  • sidecar 1개 = S3 업로드(shipper) + 실시간 서빙(Store API)

조회 — Query가 fan-out해서 합친다

왜 Sidecar+NLB — Receive는 중앙 부하, Sidecar는 분산 + 실시간 둘 다. 과거는 허브 Store Gateway 하나가 S3에서 전 클러스터 것 다 서빙(클러스터 늘어도 추가 안 됨), 실시간만 클러스터별 sidecar. 중복 업로드 없음 — 각 클러스터가 external_labels(cluster=…)로 자기 것만 한 번 올림.
Version Strategy

일부러 낮게 시작한다 — EKS 1.34

업그레이드를 실제로 해보는 것이 학습 목표. standard support 중 가장 낮은 1.34에서 출발해 1.35 → 1.36 두 번을 in-place로 연습한다.

왜 1.34인가 — 진짜 breaking change가 있다

  • 1.35 — cgroup v1 제거 · containerd 1.x 지원 마지막 · IPVS deprecated
  • 1.36 — gitRepo 볼륨 영구 비활성 · StrictIPCIDRValidation 기본 활성 · IPVS 제거
  • 착수 시점(F3·F4)에 릴리스 노트 + list-insights로 재검증하고 시작

extended support(≤1.33)로는 안 내려간다

클러스터 시간당 $0.10 → $0.60. 클러스터 2개면 월 +$730. 업그레이드 한 번 더 해보려고 낼 돈이 아니다.

버전은 전부 파일에 고정

versions.tf · addon_version · Helm version: · AMI alias. latest·* 금지. Renovate가 새 버전 PR을 만들고, 그 PR이 업그레이드 스터디 재료가 된다.

차트·애드온 하한선 — 이 넷을 확인하고 내린다

  • k8s 1.34를 지원하는가 (CRD apiVersion 불일치 방지)
  • 의존 기능이 있는가 — ArgoCD awsAuthConfig+cluster generator · Kyverno CEL 정책 타입
  • Karpenter는 EKS 호환 매트릭스를 반드시 확인
  • 노출면 있는 컴포넌트(ArgoCD·Grafana·oauth2-proxy)는 알려진 CVE 없는 버전 — 낮게 시작 학습은 내부 컴포넌트로만

Deep Dive · Karpenter

Karpenter — 클러스터마다 필수, AWS 리소스는 클러스터 생성 시 함께

Karpenter 자체 설치는 GitOps(B5-0 허브 / C3 워크로드)지만, Karpenter가 쓸 AWS 리소스는 modules/eks-cluster가 클러스터 만들 때 함께 만든다(karpenter-prep.tf). 노드 오토스케일러라 클러스터마다 하나씩 있어야 하고, 그 권한·큐가 없으면 노드를 못 띄운다.
